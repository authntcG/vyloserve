# Bugs & Limitasi Diketahui (Known Issues)

Dokumen ini berisi daftar kendala, limitasi arsitektur, dan bug spesifik OS yang *telah ditemukan* (beserta jalan keluarnya). Daftar ini sangat penting untuk mencegah developer atau asisten AI mengulangi kesalahan pencarian (*troubleshooting*) yang sama di masa mendatang.

## 1. Isu Jaringan: PostgreSQL *Timeout* Meskipun Berjalan
**Deskripsi:** Service PostgreSQL versi 18.x seringkali menunjukkan pesan "Timeout waiting for database to start" pada UI, meskipun ketika dites koneksi, databasenya hidup dan memproses query dengan lancar.
**Penyebab (Root Cause):** Konfigurasi *localhost* pada Windows modern (seperti Win 11) untuk keluarga TCP. Fungsi `check_port_in_use()` bawaan awalnya hanya mengecek koneksi jaringan IPV4 (`AF_INET`, `127.0.0.1`), padahal PostgreSQL mengikat (*binding*) listener utamanya ke IPV6 (`::1`).
**Solusi (Fixed):** File `system_utils.py -> check_port_in_use()` telah diperbaiki dengan metode Fallback: jika `127.0.0.1` gagal dikoneksikan, ia akan beralih memeriksa IPv6 `::1`. 

## 2. Isu Hak Akses (UAC) Pada `hosts` Windows
**Deskripsi:** Pembuatan *Virtual Host* otomatis memerlukan modifikasi file rahasia OS `C:\Windows\System32\drivers\etc\hosts`. Ini membutuhkan akses Administrator. Jika Python dijalankan biasa tanpa "Run as Administrator", perubahan ditolak OS.
**Solusi (Fixed):** Pada `project.py`, diterapkan sebuah fungsi fallback `_write_hosts_with_uac`. Aplikasi tidak akan error (crash), namun ia akan membangkitkan popup izin administrator bawaan OS Windows secara parsial (dengan perintah `ctypes.windll.shell32.ShellExecuteW`). Jika diiyakan (return kode > 32), data `hosts` akan disalin.

## 3. ✅ Typo *Path* Ekstraksi Apache (`con` vs `conf`) — SUDAH DIPERBAIKI (ulang)
**Deskripsi:** Instalasi Apache pernah gagal karena tidak menemukan file konfigurasi `/con/httpd.con`.
**Penyebab:** Kesalahan fatal substitusi teks (Find/Replace) pada Regex saat fase refactoring massal, mengubah kata `conf` menjadi `con`.
**Riwayat:** `core/services/apache.py` dan `core/services/ssl_manager.py` sudah benar menggunakan `conf/`. Namun audit ulang menemukan `core/services/project.py` fungsi `sync_apache_vhosts()` **masih** menulis ke folder `con/extra` (typo yang sama, regresi yang lolos dari perbaikan sebelumnya).
**Solusi (Fixed — dikonfirmasi ulang):** `os.path.join(status["path"], 'con', 'extra')` telah diganti menjadi `os.path.join(status["path"], 'conf', 'extra')` di `project.py`. Virtual host yang dibuat lewat Project Manager sekarang ter-*load* dengan benar oleh Apache.
**Catatan pencegahan regresi:** Tambahkan unit test yang memvalidasi path `conf/extra` secara eksplisit (assert pada path yang dipakai, bukan hanya hasil akhir) agar typo serupa tidak lolos lagi di masa depan tanpa terdeteksi CI.

## 4. Limitasi `pywebview` dan Komponen React Absolute Z-Index
**Deskripsi:** `pywebview` membatasi fitur-fitur manipulasi *Browser Native* tingkat lanjut. Terkadang menggunakan React *Portal* atau *Z-Index* absolut untuk `Modal` atau `Dropdown` yang terlalu di luar batas layar dapat menyebabkan elemen tersebut terpotong, karena jendela VyloServe bersifat "Frameless Desktop App" (bukan Full Browser).
**Panduan:** Gunakan elemen-elemen UI dari komponen yang sudah disediakan agar tidak menabrak limitasi render EdgeHTML/WebView2.

## 5. Menghindari `git checkout -- <file>` Sembarangan
**Limitasi AI/Developer:** Ketika melakukan refactoring (terutama oleh Agen AI), hindari penggunaan *command terminal* `git checkout -- <file>` untuk melakukan undo jika direktori kerja belum di-*commit*. Itu akan menghapus total pekerjaan yang tidak ter-*track*. **Utamakan** merevisi langsung menggunakan alat baca-tulis file secara manual.

## 6. ✅ Proses Child (`httpd.exe`/`php-cgi.exe`/`mysqld.exe`) Tidak Dimatikan Saat Quit — SUDAH DIPERBAIKI
**Deskripsi:** Dokumentasi arsitektur sebelumnya mengklaim bahwa `api.close_app()` mematikan semua manager (`php.stop_all()`, `apache.stop_server()`, dst.) sebelum aplikasi benar-benar keluar, mencegah *zombie process*.
**Status yang ditemukan saat audit:** Fungsi `perform_exit()` di `main.py` ternyata **tidak memanggil fungsi stop manapun** — ia hanya menghentikan ikon System Tray dan men-destroy window, lalu langsung `os._exit(0)`, berpotensi meninggalkan `httpd.exe`/`php-cgi.exe`/`mysqld.exe` tetap berjalan di Task Manager setelah aplikasi ditutup.
**Solusi (Fixed):** `perform_exit()` sekarang memanggil `api.apache.stop_server()`, `api.php.stop_all()`, dan `api.database.stop_all()` (masing-masing dibungkus try/except sendiri agar satu kegagalan tidak menghentikan proses cleanup lainnya) sebelum tray/window dihentikan dan `os._exit(0)` dipanggil.

## 7. ✅ Event `vylo_progress` Berpotensi "Bocor" Antar Modul Frontend — SUDAH DIPERBAIKI
**Deskripsi:** Karena seluruh halaman modul (Apache/PHP/Database/Runtimes/Git) selalu ter-*mount* bersamaan di `App.tsx` (disembunyikan lewat CSS, bukan *unmount*), dan setiap halaman memasang listener `window.addEventListener('vylo_progress', ...)` sendiri tanpa memfilter sumber event, progress bar milik satu modul (misal instalasi Apache) berpotensi ikut ter-update di modal modul lain (misal Settings PHP) jika kebetulan sedang terbuka bersamaan.
**Solusi (Fixed):**
- **Backend** (`core/api.py`): `emit_log()`/`emit_progress()` sekarang otomatis mendeteksi nama class Manager pemanggil (via `inspect`) dan menyertakannya sebagai field `source` di payload event (mis. `"source": "ApacheManager"`) — tanpa perlu mengubah satu-per-satu titik panggilan di tiap service.
- **Frontend**: setiap listener `vylo_progress` (Apache, PHP × 2, Database, Runtimes, Git) kini memfilter `e.detail.source` dan mengabaikan event yang bukan miliknya sebelum meng-update state progress.
- Sebagai bagian dari perbaikan ini, 4 titik di `core/services/project.py` yang sebelumnya memanggil `window.evaluate_js()` secara manual (bypass `emit_progress`, dengan escaping string manual yang rawan) diubah untuk memakai `self._progress()` (→ `emit_progress`) sehingga otomatis ikut mendapat `source` yang benar dan escaping JSON yang aman.
Lihat `docs/frontend_ui.md` §3.3 untuk diagram lengkap.

## 8. Tidak Ada Verifikasi Checksum/Signature pada Binary yang Diunduh (belum diperbaiki — limitasi diterima)
**Deskripsi:** Semua alur instalasi (Apache, PHP, Node, Python, Java, Go, Git, MariaDB/PostgreSQL) mengunduh binary langsung dari URL vendor tanpa memverifikasi checksum (SHA256) atau signature sebelum mengekstrak/mengeksekusinya.
**Mitigasi saat ini:** Risiko dianggap rendah karena seluruh URL sumber di-*hardcode* ke domain resmi vendor (ApacheLounge, php.net, nodejs.org, Adoptium, go.dev, GitHub Releases, archive.mariadb.org) — bukan input bebas dari user.
**Kenapa belum diotomasi-perbaiki:** Setiap vendor mempublikasikan checksum dengan format/lokasi URL yang berbeda-beda dan tidak selalu konsisten antar versi — menambahkan verifikasi otomatis berisiko membuat instalasi gagal jika format checksum vendor berubah, dan perlu pengujian menyeluruh per-vendor sebelum diaktifkan.
**Tindak lanjut (opsional, hardening — perlu keputusan eksplisit sebelum dikerjakan):** Pertimbangkan menambahkan verifikasi checksum SHA256 secara bertahap per-vendor, dimulai dari yang paling berisiko (PortableGit, karena file `.7z.exe` dieksekusi langsung).

## 9. ✅ Klaim "Zip Slip Protection" yang Tidak Akurat — SUDAH DIPERBAIKI
**Deskripsi:** Dokumentasi sebelumnya mengklaim `extract_archive()` "mencegah zip slip vulnerability", padahal audit kode menunjukkan tidak ada validasi path traversal sama sekali di `_extract_zip`/`_extract_tar_gz`.
**Solusi (Fixed):** Ditambahkan fungsi `_is_safe_extract_path()` di `core/utils/file_utils.py` yang memvalidasi setiap member arsip (baik `.zip` maupun `.tar.gz`) memakai `os.path.realpath()` sebelum diekstrak — member dengan path yang keluar dari direktori tujuan (mis. `../../evil.exe` atau path absolut) akan menggagalkan seluruh proses ekstraksi dengan `RuntimeError` yang jelas, bukan diam-diam dieksekusi.

## 10. ✅ `NameError` Tersembunyi di 3 Error Handler — SUDAH DIPERBAIKI
**Deskripsi:** Tiga tempat memakai pola `except Exception: return {..., "message": str(e)}` — variabel `e` tidak pernah terikat (`except Exception:` tanpa `as e`), sehingga saat error path benar-benar terpicu, kode melempar `NameError` baru yang menutupi pesan error asli.
**Lokasi:** `core/services/php.py` (`get_versions()`), `core/services/database.py` (`_fetch_mariadb_versions()` dan `open_path()`).
**Solusi (Fixed):** Ketiganya diganti menjadi `except Exception as e:` sehingga pesan error asli (mis. kegagalan koneksi internet) benar-benar sampai ke pengguna, bukan tertutup `NameError`.

## 11. ✅ `PROJECT_NOT_LOADED_MSG` Tidak Terdefinisi — SUDAH DIPERBAIKI
**Deskripsi:** Beberapa fallback branch di `core/api.py` (`get_projects`, `delete_project`, `retry_sync_host`, `open_in_explorer`, `update_project`) mereferensikan konstanta `PROJECT_NOT_LOADED_MSG` yang tidak pernah didefinisikan — `NameError` laten jika `self.project` pernah tidak ter-set.
**Solusi (Fixed):** Konstanta `PROJECT_NOT_LOADED_MSG = "backend.error.project_module_not_loaded"` didefinisikan di level modul `core/api.py`.

## 12. ✅ Migrasi Legacy `apache_active_version.txt` Selalu Gagal Diam-diam di Windows — SUDAH DIPERBAIKI
**Deskripsi:** Ditemukan saat menulis unit test baru untuk `_get_active_version()`: kode memanggil `os.remove(txt_file)` **di dalam** blok `with open(txt_file, 'rb') as f:` yang masih membuka file tersebut. Di Windows, menghapus file yang masih terbuka melempar `PermissionError`, yang kemudian tertelan oleh `except Exception: pass` di baris berikutnya — akibatnya migrasi dari format lama (`apache_active_version.txt`) ke format baru (`apache.json`) **selalu gagal secara diam-diam** tanpa pernah terdeteksi (fungsi selalu mengembalikan `None` alih-alih versi hasil migrasi).
**Solusi (Fixed):** `os.remove(txt_file)` dipindahkan ke luar blok `with`, dijalankan setelah file handle ditutup. Regression test ditambahkan di `tests/test_services/test_apache.py::test_get_active_version_migrates_legacy_txt_file` yang menulis file `.txt` sungguhan ke disk dan memverifikasi migrasi benar-benar berhasil serta file lama terhapus.

## 13. ✅ `uninstall_go()` Tidak Punya `return` Statement — SUDAH DIPERBAIKI
**Deskripsi:** Ditemukan saat menulis unit test untuk `RuntimesManager`: `uninstall_go()` (berbeda dari `uninstall_node`/`uninstall_python`/`uninstall_java` yang semuanya mengembalikan `{"status": "success"}`) tidak memiliki `return` sama sekali di akhir fungsi, sehingga implisit mengembalikan `None`. Frontend yang mengecek `res.status === 'success'` akan gagal (menampilkan toast error) walau proses uninstall Go sebenarnya berhasil.
**Solusi (Fixed):** Ditambahkan `return {"status": "success"}` di akhir `uninstall_go()`, konsisten dengan 3 fungsi uninstall runtime lainnya.

## 14. ✅ `install_java()`/`install_go()` Hanya Menangkap `OSError`, Melewatkan `RuntimeError` — SUDAH DIPERBAIKI
**Deskripsi:** Ditemukan saat menulis unit test untuk skenario "folder JDK tidak ditemukan setelah ekstraksi": `install_java()` melempar `RuntimeError("Folder biner JDK tidak ditemukan...")`, namun blok `except` di sekitarnya hanya menangkap `except OSError as e:` — `RuntimeError` **tidak tertangkap** dan crash keluar dari fungsi tanpa pernah dikembalikan sebagai `{"status": "error", ...}` yang rapi ke frontend. `install_go()` memakai pola except yang sama (`except OSError`), berpotensi rawan masalah serupa di masa depan meski belum ada `raise` non-OSError di dalamnya saat ini.
**Solusi (Fixed):** Kedua fungsi diubah menjadi `except Exception as e:`, konsisten dengan `install_node()`/`install_python()` yang sudah menangkap `Exception` secara umum.

## 15. ✅ Tombol Tray "Exit Engine" Melewatkan Cleanup Engine — SUDAH DIPERBAIKI
**Deskripsi:** Ditemukan saat me-refactor `main.py` agar testable: aplikasi punya **dua jalur keluar terpisah** — tombol "Quit" di UI (lewat `api.close_app()` → `perform_exit()`, yang sudah memanggil `apache.stop_server()`/`php.stop_all()`/`database.stop_all()` sejak perbaikan #6) dan menu "Exit Engine" di System Tray (`on_exit_clicked` di `setup_systray()`). Jalur kedua ini punya logic exit-nya sendiri (`is_real_exit=True; icon.stop(); window.destroy(); os._exit(0)`) yang **tidak pernah memanggil cleanup engine sama sekali** — sehingga bug zombie-process #6 sebenarnya masih bisa terjadi lewat jalur tray ini walau sudah "diperbaiki" untuk tombol Quit di UI.
**Solusi (Fixed):** `on_exit_clicked` sekarang memanggil `lifecycle.perform_exit()` yang sama persis dengan tombol Quit UI, menghilangkan jalur pintas terpisah. Sekaligus bagian dari refactor `main.py` menjadi class `AppLifecycle` (lihat §11 `docs/backend_services.md`) agar seluruh logic exit hanya ada di satu tempat dan bisa diuji lewat unit test.

## 16. ✅ Progress Instalasi Runtimes/Git Meluber Ribuan Persen Lalu "Melompat Mundur" — SUDAH DIPERBAIKI
**Deskripsi:** Saat instalasi Node.js/Python/Java/Go (dan Git) mengunduh binary dari internet, progress bar sempat menampilkan angka ribuan persen, lalu tiba-tiba turun kembali ke nilai wajar (mis. 80%) begitu fase unduhan selesai.
**Penyebab (Root Cause):** `download_advanced()`/`extract_archive()` di `core/utils/file_utils.py` memanggil `progress_cb(pct, msg)` dengan `pct` berupa persentase **ABSOLUT** (0-100, mis. 10-60 untuk unduhan, 65-80 untuk ekstraksi) — bukan fraksi `0.0-1.0`. Namun `RuntimesManager._get_cbs()` (dan `GitManager.install_git`) memperlakukan `pct` seolah fraksi, lalu menghitung ulang `start_pct + int(pct * span)`. Karena `pct` sebenarnya sudah bernilai puluhan, hasil perkaliannya meluber jauh di atas 100 (mis. `65 + int(80 * 20) = 1665`). Begitu tahap berikutnya memanggil `_emit_progress()` dengan nilai tetap (mis. 80 untuk "Mengonfigurasi environment..."), tampilan "melompat mundur" dari angka ribuan ke 80%. `core/services/apache.py`, `database.py`, dan `php.py` tidak terkena bug ini karena `prog_cb`-nya meneruskan `pct` apa adanya (kontrak yang benar).
**Solusi (Fixed):**
- **Backend** (`core/services/runtimes_manager.py`): `_get_cbs()`'s `download_cb` sekarang meng-*clamp* `pct` ke rentang `[start_pct, end_pct]` (`max(start_pct, min(pct, end_pct))`), bukan mengalikannya dengan `span`.
- **Backend** (`core/services/git_manager.py`): `download_prog_cb` di `install_git()` memakai pola clamp yang sama (`max(5, min(pct, 74))`) — bug yang sama ada di sini juga (multiplier `0.65` menutupi gejalanya sehingga tidak sampai meluber ribuan, tapi tetap salah kontrak).
- Regression test ditambahkan: `tests/test_services/test_runtimes_manager.py::test_get_cbs_clamps_out_of_range_percent` dan `tests/test_services/test_git_manager.py::test_install_git_download_progress_is_clamped_not_scaled`. Test `test_get_cbs` yang lama (memvalidasi perilaku bug lama sebagai "benar") diperbaiki agar menguji kontrak pct-absolut yang sesungguhnya.
- **Frontend** (pengaman tambahan): fungsi `frontend/src/utils/progress.ts::clampPercent()` dibuat dan dipakai di seluruh listener `vylo_progress` (`runtimes/Main.tsx`, `apache/Main.tsx`, `apache/NewProject.tsx`, `php/Main.tsx`, `php/NewInstance.tsx`, `database/Main.tsx`, `tools/git/Main.tsx`) agar UI tidak pernah menampilkan nilai progress di luar `[0, 100]` mentah-mentah, apa pun penyebabnya di sisi backend.

## 17. ✅ `'str' object has no attribute 'get'` Saat Membaca `dashboard.json` Rusak/Legacy — SUDAH DIPERBAIKI
**Deskripsi:** Alert error `"'str' object has no attribute 'get'"` bisa muncul (mis. saat men-toggle service PHP/Database dari Sidebar), meski secara manual semua fungsi tampak berjalan normal saat dicek ulang — karena pemicunya bergantung pada isi file `data/dashboard.json` di disk saat itu, bukan bug yang selalu ter-reproduksi.
**Penyebab (Root Cause):** `read_json(file_path, default_type)` di `core/utils/file_utils.py` **tidak benar-benar menjamin** tipe kembalian sesuai `default_type` — parameter itu cuma dipakai sebagai fallback saat file tidak ada/kosong/JSON tidak valid. Jika file ADA dan berisi JSON yang VALID tapi bukan objek (mis. sisa string dari file lama/rusak/hasil edit manual), `read_json()` meneruskan apa adanya. Dua caller — `PhpManager._get_preferred_versions()` (`core/services/php.py`) dan `DatabaseManager._get_preferred_dbs()` (`core/services/database.py`) — memanggil `.get('selected_php'/'selected_database', [])` **langsung** pada hasil `read_json(dashboard_json, dict)` tanpa `isinstance` check, sehingga crash persis dengan pesan `'str' object has no attribute 'get'` jika `dashboard.json` berisi string. Caller lain seperti `DashboardManager.get_config()` dan `project.py` sudah memakai `isinstance(..., dict)`/spread-check yang aman, sehingga tidak terkena bug ini.
**Solusi (Fixed):**
- **Root cause** (`core/utils/file_utils.py`): `read_json()` sekarang memvalidasi `isinstance(data, default_type)` setelah parsing — jika isi file valid JSON tapi bertipe berbeda dari yang diminta caller, otomatis fallback ke `default_type()` kosong. Ini menutup seluruh kelas bug ini untuk *semua* 10+ caller `read_json()` di codebase, bukan cuma dua yang ditemukan.
- **Defense in depth**: `_get_preferred_versions()` dan `_get_preferred_dbs()` tetap ditambahkan `isinstance(dashboard_data, dict)` eksplisit di titik pemanggilannya sendiri, konsisten dengan pola yang sudah dipakai `DashboardManager.get_config()`.
- Regression test: `tests/test_utils/test_file_utils.py::test_read_json_returns_default_when_content_type_mismatches` (memvalidasi `read_json()` tak pernah balikin tipe yang salah), `tests/test_services/test_php.py::test_get_preferred_versions_falls_back_when_dashboard_json_is_not_a_dict`, dan `tests/test_services/test_database.py::test_get_preferred_dbs_falls_back_when_dashboard_json_is_not_a_dict`. Ketiganya diverifikasi gagal saat fix di-revert sementara, sebelum fix dikembalikan.

## 18. ✅ `BackgroundProgressWidget` Menghilang Mid-Instalasi PHP (Widget Hilang, Instalasi Tetap Lanjut) — SUDAH DIPERBAIKI
**Deskripsi:** Saat instalasi PHP diminimize (widget `BackgroundProgressWidget` aktif), begitu proses mencapai tahap instalasi Composer, widget progress menghilang — padahal instalasi masih berjalan di backend dan pada akhirnya tetap berhasil (terkonfirmasi lewat modal "Tambah Versi PHP").
**Penyebab (Root Cause):** Dua bug yang saling memperparah:
1. **Backend** (`core/services/php.py::install_version`): tahap "configuring" (sebelum Composer dipasang) memanggil `self._progress(100, "backend.php.configuring")` — memakai **100%** padahal instalasi belum benar-benar selesai (Composer, langkah berikutnya, belum dipasang).
2. **Frontend** (`menu/php/Main.tsx`): listener `vylo_progress` punya logic "kalau `percent >= 100`, jadwalkan `setTimeout(() => setProgress(0), 3000)`" untuk auto-hide widget setelah instalasi *benar-benar* selesai. Timer ini **tidak pernah dibatalkan** kalau ada progress event baru yang datang sebelum 3 detik berlalu. Akibatnya: event 100% "configuring" (bug #1) menjadwalkan hide-timer; ~sepersekian detik kemudian event 95% "installing_composer" datang dan mengembalikan progress (widget tampil lagi sebentar); tapi begitu proses download `composer.phar` (blocking, tanpa progress callback, bisa makan waktu lebih dari 3 detik di koneksi lambat) belum selesai, timer basi dari langkah 1 tetap menembak `setProgress(0)` — dan `BackgroundProgressWidget` punya guard internal `if (progress <= 0 || progress >= 100) return null;` yang langsung menyembunyikan widget begitu `progress` jadi 0, walau instalasi (state `isInstalling`) sebenarnya masih `true`.
**Solusi (Fixed):**
- **Backend** (`core/services/php.py`): langkah "configuring" sekarang melapor `92%` (bukan 100%) — 100% dicadangkan khusus untuk `"backend.php.installation_complete"` yang benar-benar menandai akhir proses.
- **Frontend**, di 3 file yang berbagi pola timer yang sama (`php/Main.tsx`, `apache/Main.tsx`, `database/Main.tsx`): setiap event `vylo_progress` baru sekarang membatalkan (`clearTimeout`) timer auto-hide yang masih pending sebelum menjadwalkan yang baru — sehingga event 100%/0% yang ternyata bukan akhir proses tidak bisa lagi menyembunyikan widget di tengah instalasi, siapa pun pemicunya di masa depan. `apache.py`/`database.py` saat ini tidak punya bug backend yang sama (100% cuma dipakai di titik akhir sungguhan), tapi kerentanan frontend-nya identik sehingga tetap dikeraskan sebagai pencegahan.
- Regression test ditambahkan: `tests/test_services/test_php.py::test_php_install_version_configuring_step_is_not_terminal_progress` (memverifikasi `_progress` untuk "configuring" selalu `92`, tidak pernah `100`), diverifikasi gagal saat fix di-revert sementara.
- **Temuan sampingan**: saat menambahkan test di atas, ditemukan `test_php_install_version` yang sudah ada **tidak me-mock `_install_composer()`**, sehingga diam-diam melakukan unduhan `composer.phar` sungguhan dari internet setiap kali suite test dijalankan (test berjalan ~80 detik alih-alih ~15 detik). Ini diperbaiki dengan menambahkan `@patch.object(PhpManager, '_install_composer')` pada test tersebut — test kini hermetik dan konsisten cepat.

## 19. ✅ Log/Progress Internal Terkirim Sebagai String Mentah, Bukan Translation Key — SUDAH DIPERBAIKI
**Deskripsi:** Panel Log (System Logs) menampilkan teks Bahasa Indonesia mentah (mis. `"Memindai instalasi eksternal untuk engine 'node'..."`, `"Instalasi eksternal python (Python 3.10.11) terdeteksi pada sistem."`) walaupun bahasa aplikasi sudah di-set ke English. Ditemukan juga beberapa log/pesan yang menampilkan literal key translation-nya sendiri (mis. `"backend.git.found_external"`) karena key yang dipanggil kode tidak pernah didaftarkan di `translation.json`.
**Penyebab (Root Cause):** Dua kelas bug berbeda yang bercampur:
1. **String mentah, bukan key sama sekali.** Puluhan pemanggilan `self._log(...)`/`self._emit_log(...)`/`self._progress(...)`/`self._emit_progress(...)` di `core/services/runtimes_manager.py`, `project.py`, `database.py`, dan `core/api.py` mengirim f-string/`.format()` Bahasa Indonesia langsung sebagai argumen `msg`, bukan translation key `"backend.xxx.yyy"` — padahal key yang sepadan **sudah tersedia** di `translation.json` sejak awal (locale sudah disiapkan lebih dulu, kode-nya yang belum pernah memakainya). Audit awal (yang melahirkan perbaikan i18n sebelumnya) hanya memeriksa field `"message"` pada return value API dan string di `.tsx`, sehingga kelas bug ini — pesan log/progress *real-time*, bukan return value — lolos tidak terdeteksi.
2. **Root cause spesifik `runtimes_manager.py`:** wrapper privat `_emit_log(self, msg, level="info")`/`_emit_progress(self, percent, msg)` di file ini **tidak punya parameter `args` sama sekali** — berbeda dari wrapper `_log()`/`_progress()` di `project.py`/`database.py`/`php.py`/`git_manager.py` yang semuanya sudah menerima `args: dict = None` dan meneruskannya ke `self.api.emit_log/emit_progress`. Tanpa slot `args`, mustahil melakukan interpolasi (`{{engine}}`, `{{version}}`) lewat translation key, sehingga kode di file ini "terpaksa" ditulis pakai f-string mentah sebagai jalan pintas — bug arsitektur yang mendorong lahirnya bug #1 secara berulang khusus di file ini.
3. **Key hilang/typo, terpisah dari dua di atas:** beberapa pemanggilan sudah benar memakai bentuk key, tapi key-nya tidak pernah didaftarkan di `translation.json` sama sekali (`backend.git.found_external`, `backend.apache.starting_service`, `backend.php.starting_service`, `backend.apache.stopping_service`, `backend.php.stopping_service`, `backend.api.closing_app`), atau memakai nama konstanta yang menyimpang dari key aslinya (`DB_NOT_FOUND_MSG = "backend.database.db_not_found"` padahal key yang benar-benar terdaftar adalah `backend.database.not_found`). i18next diam-diam fallback menampilkan key mentah tanpa crash, sehingga bug jenis ini nyaris tidak pernah terlihat kecuali membaca log secara langsung.
**Solusi (Fixed):**
- Seluruh pemanggilan log/progress mentah di `core/api.py` dan `core/services/{runtimes_manager,project,database,git_manager,php,apache,dashboard,settings}.py` diganti memakai translation key + `args` (lihat riwayat commit untuk daftar lengkap — mencakup ~45 titik di `runtimes_manager.py` saja).
- `RuntimesManager._emit_log()`/`_emit_progress()` diberi parameter `args: dict = None` dan meneruskannya ke `self.api.emit_log/emit_progress`, konsisten dengan wrapper di service lain. Closure `log_cb`/`download_cb` di `_get_cbs()` juga diperbarui agar ikut meneruskan `args`.
- Semua key yang hilang ditambahkan ke **kedua** `frontend/src/locales/{en,id}/translation.json`; key yang salah nama/typo diperbaiki agar konsisten dengan definisi aslinya.
- **Regression test permanen ditambahkan:** `tests/test_i18n_keys.py` — memindai setiap literal `"backend.xxx.yyy"` di `core/` dan gagal jika key tersebut tidak terdaftar di salah satu (atau kedua) file locale. Ini mencegah kelas bug #3 (key hilang/typo) terulang secara otomatis di CI, tanpa bergantung pada disiplin baca dokumentasi. **Test ini tidak bisa mendeteksi kelas bug #1** (string mentah yang belum pernah diubah jadi key sama sekali) — untuk itu tetap perlu review manual atau menjalankan aplikasi dan membaca Log Panel langsung di kedua bahasa.
- Dokumentasi diperbarui agar aturan "dilarang hardcode" ditegaskan berlaku untuk log/progress internal juga, bukan cuma field `"message"`: lihat `AGENTS.md` §"Arsitektur Multi-Bahasa (i18n)", `docs/backend_services.md` §2.2, dan `docs/ai_development_guide.md` §6.3 & §8 (Definition of Done).

## 20. ✅ CSS Cascade Layers Membuat Semua `text-[Npx]` pada Ikon Material Symbols Tidak Berfungsi — SUDAH DIPERBAIKI
**Deskripsi:** Di seluruh aplikasi, elemen `<span className="material-symbols-outlined text-[Npx]">` (ikon dengan ukuran custom lewat Tailwind arbitrary value) selalu tampil di ukuran default 24px, tidak peduli angka `N` yang dipasang (14px, 16px, 18px, 20px, 32px, dst — semuanya computed jadi 24px). Ditemukan saat memperbaiki bug UI Sidebar mode collapsed: badge kecil `chevron_right` yang seharusnya 12px malah render 24px dan menabrak/merusak tampilan ikon "construction" di sebelahnya.
**Penyebab (Root Cause):** Proyek memakai Tailwind v4 (`@import "tailwindcss";` di `src/index.css`), yang membungkus seluruh utility class-nya (termasuk `text-[Npx]`) di dalam **CSS Cascade Layer** (`@layer theme, base, components, utilities;`). Sesuai spesifikasi CSS Cascade Layers, **rule yang TIDAK berada di dalam layer manapun SELALU menang atas rule di dalam layer manapun**, berapa pun urutan importnya secara fisik dan meski spesifisitas selector-nya sama. `material-symbols/outlined.css` diimport polos lewat `import 'material-symbols/outlined.css'` di `main.tsx` (import JS biasa, bukan CSS `@import`), sehingga rule bawaannya, `.material-symbols-outlined { font-size: 24px; }`, tidak pernah ikut sistem layer Tailwind — otomatis selalu menang atas utility `.text-\[Npx\] { font-size: Npx; }` mana pun, walau class Tailwind tersebut ADA dan BENAR terpasang di JSX. Percobaan pertama untuk memperbaiki ini (memindah urutan `import` di `main.tsx` supaya material-symbols "diimport lebih dulu") **tidak menyelesaikan masalah** — dikonfirmasi lewat inspeksi `getComputedStyle()` di browser bahwa font-size tetap 24px setelah reorder, karena cascade layer tidak peduli urutan source sama sekali selama salah satu pihak unlayered.
**Solusi (Fixed):**
- `src/index.css`: `material-symbols/outlined.css` sekarang diimport lewat CSS `@import "material-symbols/outlined.css" layer(base);` (bukan import JS di `main.tsx`), sehingga ikut sistem cascade layer Tailwind di layer `base` — prioritas terendah di antara layer bawaan Tailwind, sehingga `@layer utilities` (termasuk semua `text-[Npx]`) benar-benar bisa menindihnya.
- `main.tsx`: baris `import 'material-symbols/outlined.css';` dihapus (dipindah ke `index.css`) untuk menghindari duplikasi.
- **Diverifikasi lewat `getComputedStyle()` langsung di browser** (Playwright + Microsoft Edge lokal, bukan cuma visual): sebelum fix, semua ikon `text-[14/16/18/20/32px]` di berbagai halaman computed jadi 24px; setelah fix, semuanya sesuai ukuran aslinya masing-masing. Tidak ada regression test otomatis untuk bug ini (proyek belum punya test suite frontend/browser-based — hanya `pytest` untuk backend Python) — verifikasi ulang manual di browser tetap diperlukan kalau pipeline import CSS global berubah lagi.
- Dokumentasi ditambahkan: `docs/frontend_ui.md` §15 (aturan wajib `layer()` untuk CSS pihak ketiga baru + cara verifikasi cepat lewat `getComputedStyle()`), dan `docs/frontend_ui.md` §2.4 (konvensi badge ukuran-kecil pakai inline `style={{fontSize}}`, bukan `text-[Npx]`, untuk kasus yang butuh override lokal cepat tanpa bergantung urutan cascade).
- **Follow-up bug (ditemukan lewat SonarQube, rule `css:S8778`):** fix di atas sendiri sempat menaruh `@import "material-symbols/outlined.css" layer(base);` **setelah** `@tailwind base; @tailwind components; @tailwind utilities;` di `index.css` — CSS mewajibkan SEMUA `@import` berada paling atas file, sebelum rule non-`@import` apa pun (kecuali `@charset`). Posisi salah membuat `@import` tersebut invalid/diabaikan browser. Diperbaiki dengan memindahkannya jadi baris kedua, tepat setelah `@import "tailwindcss";`. Pelajaran: setiap menambah `@import` baru ber-`layer()`, taruh selalu di **paling atas** file, sebelum rule apa pun lainnya, jangan cuma "sebelum `@theme`" atau posisi lain yang terasa logis secara pembacaan.

## 22. ✅ Tombol Start/Stop Server Tidak Sinkron Antar Halaman Modul — SUDAH DIPERBAIKI
**Deskripsi:** Ketika service (Apache/PHP/Database) dinyalakan lewat tombol "Start Selected"/"Stop Selected" di halaman Dashboard, service-nya benar-benar menyala/mati di backend — tapi tombol toggle "Start Server"/"Stop Server" di halaman modul terkait (`apache/Main.tsx`, `php/Main.tsx`, `database/Main.tsx`) tetap menampilkan state lama sampai aplikasi di-restart penuh.
**Penyebab (Root Cause):** Seluruh halaman saling menyinkronkan status service lewat custom event `service_status_changed` yang dibaca dari `e.detail.service`/`e.detail.running`. Handler `handleToggleAll` di `dashboard/Main.tsx` men-dispatch event ini sebagai `new Event('service_status_changed')` **tanpa payload `detail`**, sehingga di setiap listener modul (`apache/Main.tsx`, `php/Main.tsx`) ekspresi `e.detail.service` melempar `TypeError` (karena `e.detail` adalah `undefined`) sebelum sempat memperbarui state lokal — errornya senyap karena terjadi di dalam callback event listener, tidak pernah terlihat di UI. Selain itu, tombol toggle di `apache/Main.tsx` sendiri (`handleToggleServer`) ternyata **tidak pernah** men-dispatch `service_status_changed` sama sekali — hanya mengubah state lokalnya sendiri — sehingga start/stop dari halaman Apache pun tidak pernah tersebar ke halaman lain (Dashboard/Sidebar/PHP/Database). Bug ini tidak kelihatan dari Dashboard atau Sidebar sendiri karena keduanya juga melakukan polling berkala (Dashboard tiap 3 detik, Sidebar tiap 2 detik) yang menutupi event yang gagal; halaman modul (apache/php/database) tidak punya polling fallback, jadi murni bergantung pada event yang justru rusak.
**Solusi (Fixed):**
- `dashboard/Main.tsx` `handleToggleAll`: event sekarang di-dispatch sebagai `new CustomEvent('service_status_changed', { detail: { service: 'all' } })`.
- `dashboard/Main.tsx`: seluruh listener di `apache/Main.tsx`, `php/Main.tsx`, `database/Main.tsx` diperbarui agar (a) memakai optional chaining (`e.detail?.service`) supaya tidak crash kalau `detail` kosong, dan (b) juga bereaksi terhadap `service: 'all'`, tidak cuma nama service spesifiknya sendiri.
- `apache/Main.tsx` `handleToggleServer`: sekarang ikut men-dispatch `service_status_changed` dengan `detail: { service: 'apache', running: ... }` setelah toggle berhasil, konsisten dengan pola yang sudah dipakai `php/Main.tsx` dan `database/Main.tsx`.
- Pelajaran untuk ke depannya: setiap kali men-dispatch `service_status_changed` di titik baru, **wajib** selalu sertakan `detail: { service: '<nama_service_atau_all>' }` — jangan pernah dispatch sebagai `new Event(...)` polos tanpa payload, karena semua listener yang ada saat ini mengasumsikan `detail` selalu tersedia.

## 24. ✅ Lokasi Folder Default di Modal "New Project" Hilang Setiap Restart Aplikasi — SUDAH DIPERBAIKI
**Deskripsi:** Field lokasi instalasi (workspace folder) di modal Apache "New Project" (`apache/NewProject.tsx`) seharusnya mengingat folder terakhir dipakai user, tapi setiap aplikasi ditutup dan dibuka ulang, field ini kembali kosong seolah-olah belum pernah diisi sama sekali.
**Penyebab (Root Cause):** Nilai ini disimpan lewat `localStorage.setItem('vylo_install_loc', ...)` di browser, bukan lewat backend. Aplikasi ini berjalan di dalam shell **pywebview dengan backend EdgeChromium (WebView2)**, dan `main.py` tidak pernah mengonfigurasi `storage_path` eksplisit saat memanggil `webview.start()`/`webview.create_window()`. Tanpa `storage_path`, WebView2 memakai folder profil sementara (ephemeral user-data folder) yang tidak dijamin bertahan antar sesi aplikasi — sehingga `localStorage` di app ini pada praktiknya *tidak reliable* untuk penyimpanan jangka panjang, meski API-nya sama seperti browser biasa. Grep di seluruh `frontend/src` mengonfirmasi ini adalah **satu-satunya** pemakaian `localStorage` di seluruh aplikasi — semua state lain yang perlu persisten sudah lewat backend (`data/*.json`).
**Solusi (Fixed):**
- Proyek ini sudah punya mekanisme penyimpanan preferensi global yang generik dan extensible: `core/services/settings.py` (`SettingsManager.get_settings()`/`save_settings()`) yang membaca/menulis `data/settings.json` dengan pola **auto-merge** (key baru otomatis fallback ke default kalau belum ada di file lama, dan `save_settings()` mem-merge parsial tanpa menimpa key lain) — sebelumnya cuma dipakai untuk key `"language"`. Sudah ada juga endpoint pywebview-nya: `get_app_settings()`/`save_app_settings()` di `core/api.py`.
- `core/services/settings.py`: menambahkan key baru `"default_apache_install_location": ""` ke `default_config`.
- `apache/NewProject.tsx`: `localStorage.getItem/setItem('vylo_install_loc', ...)` diganti dengan memuat nilainya lewat `get_app_settings()` di `useEffect` saat mount, dan menyimpannya lewat `save_app_settings({ default_apache_install_location: val })` setiap kali user mengubah lokasi (baik lewat input manual maupun tombol "Browse").
- **Pelajaran untuk ke depannya:** di app pywebview ini, `localStorage`/`sessionStorage` browser **tidak boleh** dipakai untuk apa pun yang perlu bertahan antar sesi aplikasi — selalu pakai `get_app_settings()`/`save_app_settings()` (untuk preferensi umum) atau manager JSON khusus di `data/*.json` (untuk data terstruktur seperti project/database/dsb). Kalau ada preferensi baru yang perlu "diingat" ke depannya (tema, filter terakhir, dsb.), tambahkan saja key baru ke `default_config` di `settings.py` — jangan buat file JSON baru di `data/` kecuali datanya benar-benar berbeda struktur/domain (mis. daftar project, daftar database) dari sekadar preferensi UI sederhana.

## 25. ✅ `LogFileViewerModal` Fetch Berulang-ulang Setiap Render Karena `t` Tidak Stabil — SUDAH DIPERBAIKI
**Deskripsi:** Ditemukan lewat unit test saat membangun fitur "lihat isi file log Apache/Database di dalam aplikasi" (`LogFileViewerModal.tsx`, dipakai di `apache/Settings.tsx` dan `database/Main.tsx`): komponen ini memanggil API `fetchContent()` **berkali-kali** (3x pada test render awal, 6x setelah klik tombol Refresh sekali) padahal seharusnya cuma 1x per pembukaan modal / 1x per klik Refresh.
**Penyebab (Root Cause):** Fungsi `loadContent` dibungkus `useCallback(..., [fetchContent, t])`, lalu `useEffect(() => { if (isOpen) loadContent(); }, [isOpen, loadContent])` dipakai untuk memicu fetch otomatis saat modal dibuka. Masalahnya: `t` dari `useTranslation()` **tidak dijamin stabil identitasnya antar render** (mock `useTranslation()` di `tests/setup.ts` sengaja membuat fungsi `t` baru setiap kali dipanggil, meniru kemungkinan perilaku serupa di react-i18next asli tergantung konfigurasi). Setiap kali `t` berganti identitas → `loadContent` ikut berganti identitas (karena ada di deps-nya) → `useEffect` yang bergantung pada `loadContent` mendeteksi perubahan deps → fetch dipanggil ulang → `setIsLoading()`/`setContent()` memicu render baru → siklus berulang sampai state stabil. Efeknya murni performa/beban API berlebih (bukan crash), tapi tetap nyata: setiap buka modal log memanggil backend berkali-kali secara sia-sia.
**Solusi (Fixed):** `t` dikeluarkan dari dependency array `useCallback` (`[fetchContent]` saja, dengan `// eslint-disable-next-line react-hooks/exhaustive-deps` dan komentar penjelasan) — `t` tetap dipakai di dalam closure-nya, hanya tidak lagi memicu re-creation function setiap render. Diverifikasi lewat unit test yang menghitung persis jumlah pemanggilan `fetchContent` (`toHaveBeenCalledTimes(1)` setelah buka, `toHaveBeenCalledTimes(2)` setelah 1x klik Refresh) — test ini akan langsung merah lagi kalau pola bug ini terulang.
- **Pelajaran untuk ke depannya:** kalau sebuah `useEffect` memicu operasi dengan efek samping (fetch API, dispatch state, dst.) berdasarkan sebuah `useCallback`, pastikan SEMUA dependency `useCallback` tersebut benar-benar stabil identitasnya antar render (props yang berasal dari `useCallback`/`useMemo` di parent, atau primitif) — jangan masukkan `t` dari `useTranslation()` ke deps sebuah `useCallback` yang dipakai untuk memicu efek samping otomatis, kecuali sudah dipastikan stabil. Test dengan `toHaveBeenCalledTimes()` yang presisi (bukan `toHaveBeenCalled()` longgar) adalah cara paling efektif menangkap kelas bug ini karena test biasa yang cuma cek "akhirnya data muncul" tidak akan mendeteksi pemanggilan berulang yang sia-sia.

## 26. ✅ Filter "System Logs" Terlihat Tidak Tersimpan Saat Semua Checkbox Di-uncheck, dan Kategori Tidak Bisa Dipisah Log Sistem vs File Log — SUDAH DIPERBAIKI
**Deskripsi:** Dua masalah terkait modal pengaturan "System Logs" ditemukan oleh user lewat pengetesan manual:
1. Kalau user meng-uncheck SEMUA checkbox di satu kelompok (level atau kategori) lalu klik Save, saat modal dibuka lagi semua checkbox kembali tercentang seolah-olah pilihan user tidak pernah tersimpan — padahal `save_app_settings()` benar-benar terpanggil dan `data/settings.json` benar-benar tertulis.
2. User bertanya: kalau kategori "Apache" di-uncheck, apakah itu cuma mematikan baris dari file `error_log`/`access_log`, atau ikut mematikan pesan sistem Apache biasa (install/start/stop/error)? Jawabannya sebelum fix ini: **keduanya ikut mati sekaligus**, karena tidak ada cara memisahkan keduanya — kategori terlalu kasar ("non-atomic").

**Penyebab (Root Cause) — masalah 1:** Desain awal memakai **array kosong (`[]`) sebagai sentinel ganda** untuk dua makna berbeda: "belum pernah dikustomisasi user, tampilkan semua" DAN "user sengaja uncheck semua, jangan tampilkan apa pun". Saat modal Apply menyimpan, kode secara sengaja "mengompres" pilihan balik jadi `[]` setiap kali SEMUA checkbox tercentang (`logLevels.length === ALL_LOG_LEVEL_KEYS.length ? [] : logLevels`) — tapi kalau user uncheck SEMUA (bukan checked semua), `logLevels` JUGA berakhir jadi array kosong secara alami, sehingga tidak bisa dibedakan dari kasus "checked semua". ## 29. ✅ Korupsi Encoding (Mojibake) pada File Dokumentasi `.md` — SUDAH DIPERBAIKI
**Deskripsi:** Ditemukan dua kejadian korupsi encoding UTF-8 yang terpisah, keduanya pada file `docs/*.md`/`AGENTS.md` (tidak pernah ditemukan di file kode `.py`/`.tsx`/`.json`):

2. **Sudah ter-commit ke Git (HEAD):** Entri bug #27 di `docs/known_bugs.md` (ditulis di commit sebelumnya) berisi 2 byte NULL (`\x00`) tersisip di antara paragraf, 1 karakter replacement (`�`, U+FFFD) di judul, **dan** setiap tanda kutip-balik (`` ` ``) di seluruh isi entri berubah jadi backslash tunggal (`` ` ``→`\`) — beberapa di antaranya (yang diikuti huruf `t`) bahkan berubah jadi karakter TAB literal (`` `t ``→ tab), mengindikasikan isi entri ini sempat melalui proses *escape-sequence decoding* yang salah (`\t` diinterpretasikan sebagai tab) di atas kerusakan backtick→backslash yang sudah terjadi lebih dulu.

Kejadian #2 (backtick→backslash, lalu `\t`→TAB) menunjukkan kerusakan berlapis: kemungkinan besar melalui alat berbasis skrip yang memproses *escape sequence* mentah, bukan sekadar salah code page tunggal.
**Solusi (Fixed):**
- 4 file working-tree yang korup di-*restore* ke versi `HEAD` (`git checkout HEAD -- <file>`) sebagai baseline bersih, lalu konten baru (fitur Auto-Updater, dsb.) ditulis ulang secara manual dengan karakter UTF-8 yang benar — **bukan** mencoba mendekode-balik teks mojibake secara algoritmik (dicoba lewat reversal cp1252↔UTF-8 berlapis, terbukti tidak reliable karena sebagian file sudah bercampur teks yang benar dan yang rusak dengan jumlah "putaran" korupsi yang tidak konsisten per karakter).
- Entri bug #27 di `docs/known_bugs.md` (HEAD) ditulis ulang manual mempertahankan makna aslinya (masih bisa dipahami dari konteks), dengan backtick, em dash, dan emoji `✅` yang benar, serta byte NULL dihapus.
**Pelajaran untuk ke depannya:**
- **Jangan pernah** mengedit file `.md`/teks berisi emoji atau karakter non-ASCII lewat `Set-Content`/`Add-Content`/`Out-File` di PowerShell tanpa `-Encoding utf8` eksplisit — lihat juga peringatan yang sama soal `.gitleaksignore` yang sebelumnya tersimpan sebagai UTF-16 (sudah diperbaiki di sesi yang sama dengan penemuan bug ini).
- Setelah sebuah sesi AI melakukan editing besar-besaran ke file dokumentasi (terutama yang banyak memakai emoji/simbol), verifikasi cepat lewat pengecekan byte NULL/`U+FFFD` dan bandingkan `git diff` sebelum commit — jangan asumsikan `file <nama>` yang melaporkan "ASCII text"/"UTF-8 text" berarti kontennya pasti benar; heuristik `file` bisa salah menebak ("data") pada file yang justru valid UTF-8, dan sebaliknya tidak selalu menangkap mojibake yang tetap berupa UTF-8 valid secara teknis.
- **⚠️ Kekambuhan (ditemukan lagi saat audit dokumentasi menyeluruh berikutnya):** Pola kerusakan yang SAMA PERSIS (backtick diikuti huruf tertentu berubah jadi karakter kontrol C-style: `` `a``→BEL `\x07`, `` `b``→Backspace `\x08`, `` `t``→TAB `\x09`) ditemukan lagi di entri `docs/known_bugs.md` lain (bug Modal Alert/Toast) dan di `docs/frontend_ui.md` §6.7 (kata `backdrop-blur-xl`, `bg-white/70`, `toast-out`, `await` kehilangan huruf pertamanya, diganti karakter kontrol literal). Ini membuktikan sumber kerusakannya **belum benar-benar hilang** dari alur kerja proyek ini — kemungkinan besar sebuah tool/skrip (bukan `Edit`/`Write` milik Claude Code, yang sudah terverifikasi UTF-8-safe) yang menginterpretasikan backtick+huruf sebagai escape sequence C/shell (mis. `printf`/`echo -e` tanpa penanganan backtick, atau proses template string yang keliru). **Jangan anggap insiden ini sudah final diperbaiki** hanya karena pernah didokumentasikan sekali — tetap jalankan pengecekan `grep -rlP '[\x00-\x08\x0b\x0c\x0e-\x1f]' docs/*.md AGENTS.md` sesekali, terutama setelah sesi kerja yang melibatkan banyak penulisan ulang file dokumentasi oleh AI (termasuk oleh subagent/fork).

## 34. ✅ Share Project via Zrok Gagal Total: "URL Publik Tidak Ditemukan" Padahal Share Sukses Dibuat di Cloud Zrok (Berakhir Bad Gateway) — SUDAH DIPERBAIKI
**Deskripsi:** Dilaporkan user: saat mencoba men-share project lokal (vhost `laravel.test`) lewat fitur Tunnels, aplikasi menampilkan alert error "tidak dapat menemukan url publik dari zrok" dan tidak ada entri muncul di daftar "tautan aktif" VyloServe. Namun saat user memeriksa langsung dashboard zrok (`https://api-v1.zrok.io/`), ternyata ADA share yang tercatat dengan target `http://127.0.0.1:80` — dan ketika URL share tersebut diakses, browser menampilkan **Bad Gateway**.
**Penyebab (Root Cause):** `start_zrok_share()` membaca output `zrok.exe share public ... --headless` lewat `proc.stdout.readline()` yang **blocking di thread utama**, dengan batas waktu cuma 15 detik dan SATU pola regex kaku (`"access your zrok share:\s+URL"`). Dua kelemahan ini bergabung menghasilkan persis gejala yang dilaporkan:
1. **Pembacaan stdout rentan tersandera buffering OS/pipe**: kalau output `zrok.exe` tidak langsung ter-*flush* per baris (umum terjadi saat stdout proses diarahkan ke pipe, bukan terminal interaktif), `readline()` bisa menunggu lama lalu tiba-tiba menerima banyak baris sekaligus — bisa saja PERSIS setelah batas waktu 15 detik keburu habis. Padahal di sisi zrok, share **sudah benar-benar terbentuk** di cloud (makanya tetap muncul di dashboard `api-v1.zrok.io`) — hanya saja VyloServe gagal membaca baris URL-nya tepat waktu, lalu memanggil `proc.kill()` dan melaporkan `url_not_found` ke user.
2. **Proses lokal yang sudah di-*kill* meninggalkan share "yatim"**: setelah `proc.kill()`, share di sisi cloud zrok tidak langsung hilang dari dashboard (tetap tercatat untuk sesaat), tapi backend lokalnya (proses `zrok.exe` di komputer user) sudah mati. Akibatnya kalau user mengakses URL share tersebut (ditemukan lewat dashboard), zrok edge tidak bisa meneruskan request ke backend yang sudah tidak ada → **Bad Gateway**. Ini BUKAN soal `ServerAlias`/vhost Apache yang salah (mekanisme `update_project({"tunnel_url": ...})` → `sync_apache_vhosts()` sudah benar dirancang) — kode itu bahkan **tidak pernah sempat jalan** karena fungsi sudah `return` error di baris deteksi URL, sebelum mencapai baris injeksi alias.
**Solusi (Fixed):**
- Pembacaan `stdout` dipindah ke **thread terpisah** yang terus-menerus mengiterasi `proc.stdout` dan menaruh tiap baris ke `queue.Queue()` — loop deteksi di thread utama sekarang `queue.get(timeout=...)`, tidak lagi `readline()` blocking langsung ke pipe proses. Ini menghilangkan risiko tersandera buffering OS, karena pembacaan aktual tidak lagi terikat pada window waktu deteksi.
- Batas waktu dinaikkan dari 15 detik → 30 detik (`ZROK_SHARE_DETECT_TIMEOUT_SECONDS`, konstanta bernama, bukan angka ajaib) — memberi ruang lebih untuk handshake OpenZiti yang kadang lambat.
- Ditambahkan **pola regex cadangan** (`https?://[a-z0-9.-]*zrok\.io\S*`) yang menangkap URL domain zrok apa pun, dipakai sebagai fallback kalau frasa persis "access your zrok share:" berubah di versi `zrok.exe` yang berbeda.
- **Setiap baris stdout sekarang di-log ke System Logs SELAMA fase deteksi juga** (dulu hanya SETELAH URL berhasil ditemukan) — kalau deteksi gagal lagi di masa depan, output asli `zrok.exe` tetap terlihat untuk diagnosis, tidak hilang begitu saja.
- Ditambahkan 3 test regresi baru: pola cadangan menangkap frasa berbeda, timeout benar-benar men-*kill* proses dan tidak meninggalkan entri di `active_shares`, dan setiap baris ter-log selama fase deteksi.
**Pelajaran untuk ke depannya:** Membaca `stdout` sebuah subprocess interaktif (terutama binary pihak ketiga yang perilaku buffering-nya tidak kita kontrol) **jangan pernah** dilakukan lewat `readline()` blocking langsung di thread yang juga menjalankan logika timeout berbasis wall-clock — kombinasi ini rawan race antara "kapan OS benar-benar mem-flush buffer pipe" vs "kapan kode kita menyerah menunggu". Pola yang aman: thread pembaca khusus yang terus mengisi `queue.Queue()`, dipisah dari logika timeout/keputusan di thread lain yang tinggal `queue.get(timeout=...)`. Selain itu, kalau proses eksternal (zrok, atau binary pihak ketiga manapun) punya kemungkinan mengubah format output-nya antar versi, selalu sediakan pola deteksi cadangan yang lebih longgar, jangan bergantung pada satu frasa persis.

> ⚠️ **Koreksi jujur (lihat #35):** Perbaikan di atas (thread terpisah + timeout 30 detik + regex cadangan) adalah hardening yang VALID dan tetap dipertahankan, tapi setelah user melaporkan **bug yang sama persis masih terjadi**, investigasi lanjutan dengan benar-benar MENJALANKAN `zrok.exe` v2.0.7 asli (bukan cuma membaca kode) mengungkap bahwa analisis "buffering/timeout" di atas **bukan akar masalah sebenarnya** — root cause sesungguhnya jauh lebih sederhana dan fundamental: regex-nya mencari frasa dan format URL yang **sama sekali tidak pernah muncul** di output zrok v2, terlepas dari berapa lama ditunggu. Lihat #35 untuk detail lengkap dan perbaikan yang benar-benar menyelesaikan masalah ini.

## 35. ✅ Akar Masalah Sesungguhnya dari Bug #34: `zrok.exe` v2 Mencetak Log sebagai JSON Terstruktur, Bukan Teks Biasa — Regex Lama Tidak Mungkin Pernah Match — SUDAH DIPERBAIKI

Root cause #34 (buffering/timing) terdengar sangat meyakinkan dan merupakan kelas bug yang memang nyata di dunia nyata — tapi dalam kasus ini sama sekali bukan penyebabnya. Begitu binary asli (`bin/zrok/zrok.exe`) ternyata tersedia di lingkungan kerja, menjalankannya langsung (`zrok.exe share public http://127.0.0.1:PORT --headless`, tangkap stdout-nya) menyelesaikan investigasi dalam hitungan menit dan memberi kepastian 100% — jauh lebih cepat dan akurat daripada menebak dari nama fungsi/variabel atau asumsi format log yang "terlihat masuk akal". **Kalau ada binary/tool eksternal yang tersedia untuk diajak bicara langsung, selalu coba itu dulu sebelum menganalisis lebih lanjut dari kode semata** — terutama untuk bug yang sudah "diperbaiki" sekali tapi ternyata masih terjadi, itu sinyal kuat bahwa diagnosis sebelumnya salah arah, bukan sekadar perlu tuning parameter (timeout/retry) lebih lanjut.

## 38. ⚠️ Insiden: `git checkout --` Menghapus 89 Key Terjemahan yang Belum Pernah Di-*commit* — SUDAH DIPULIHKAN
**Deskripsi:** Saat menambah test paritas i18n baru (`frontend/tests/i18n.test.ts`), sebuah eksperimen validasi memakai `json.dump(..., indent=2)` untuk memformat ulang `id/translation.json` secara tidak sengaja mengubah SELURUH indentasi file dari 4 spasi menjadi 2 spasi. Untuk "membatalkan" eksperimen itu, perintah `git checkout -- frontend/src/locales/id/translation.json` dijalankan — tapi karena file ini statusnya `M` (modified, **belum pernah di-commit**) sejak beberapa sesi sebelumnya, perintah tersebut mengembalikan file ke versi commit terakhir (`733f783`), **menghapus 89 key terjemahan Bahasa Indonesia** yang sudah ada di working tree (seluruh UI & backend untuk fitur Tunnels/Zrok, beberapa pesan progres unduhan Runtimes, dan beberapa key lain) — bukan cuma membatalkan eksperimen `json.dump` yang baru saja dijalankan.
**Penyebab (Root Cause):** Asumsi keliru bahwa `git checkout -- <file>` adalah operasi "undo" yang aman untuk membatalkan satu kesalahan kecil. Pada file yang statusnya `M` (bukan file baru/belum tracked), perintah ini **selalu** mengembalikan ke snapshot commit terakhir, menghapus **SEMUA** working-tree change pada file itu tanpa pandang bulu — termasuk pekerjaan sah dari sesi-sesi sebelumnya yang belum sempat di-commit. Tidak ada mekanisme git (stash, reflog) yang bisa memulihkan perubahan working-tree yang belum pernah di-commit; reflog hanya mencatat commit, bukan edit file yang belum di-stage/commit.
**Solusi (Fixed):**
- Kerugian dipulihkan secara manual: 89 key dibangun ulang dengan menerjemahkan nilai Inggris dari `en/translation.json` (yang tidak terdampak) ke Bahasa Indonesia, mengikuti gaya/istilah yang sudah mapan di proyek ini (terutama untuk domain Zrok/Tunnels, yang sudah banyak dibahas di sesi-sesi sebelumnya).
- Setiap key disisipkan lewat Edit bertarget (bukan `json.dump` ulang) untuk menjaga indentasi 4-spasi asli file dan meminimalkan diff — hasil akhirnya tervalidasi 1:1 lewat script Python yang membandingkan seluruh dot-path key set `en` vs `id` (0 key hilang, 0 key yatim, total 1040 = 1040 di kedua file).
- Test paritas i18n baru (lihat entri enhancement terkait) langsung dijalankan ulang untuk mengonfirmasi tidak ada lagi key yang hilang setelah pemulihan.
- Ditambahkan **Aturan Strict #8** baru di `AGENTS.md` yang melarang `git checkout --`/`git restore`/`git reset --hard` pada file berstatus `M` hanya untuk membatalkan eksperimen kecil, dan mewajibkan backup manual atau edit bertarget sebagai gantinya.
**Pelajaran untuk ke depannya:** Sebelum menjalankan operasi apa pun yang bisa membuang isi file (`git checkout --`, `git restore`, menulis ulang seluruh file via `json.dump`/`write()` penuh), **selalu** tanya: "apakah file ini punya perubahan working-tree yang belum pernah di-commit, dan seberapa besar?" (`git diff --stat <file>` dulu). Untuk eksperimen validasi yang berisiko merusak file asli (mis. "coba rusak dulu untuk membuktikan test menangkapnya"), **jangan** operasikan file aslinya secara langsung dengan operasi yang me-*rewrite* isi penuh — lakukan modifikasi bertarget (text replace pada bagian kecil yang relevan saja) seperti yang sudah dipraktikkan berulang kali di sesi ini untuk validasi regression test lain (lihat entri #36, #37) — pendekatan itu terbukti aman karena hanya menyentuh baris yang relevan, bukan menimpa ulang seluruh struktur file.

## 39. ✅ `detect_framework()` Salah Mendeteksi Project Custom Berbasis Zend (dan Project Raw Apapun) sebagai Laravel — SUDAH DIPERBAIKI
**Deskripsi:** User melaporkan bahwa saat menambahkan project existing lewat menu Apache, modul kadang mendeteksi project raw PHP atau project dengan framework custom berbasis Zend yang dimodifikasi (contoh nyata: `D:\Projects\TLKM\PHP\utonline`) sebagai framework **Laravel**. Akibatnya salah: `frontend/src/menu/apache/NewProject.tsx` (`detectFrameworkForPath()`) secara otomatis menambahkan suffix `/public` ke document root setiap kali `detect_framework()` mengembalikan `"laravel"` atau `"codeigniter"` — untuk project yang sebenarnya bukan Laravel, ini membuat Apache mengarah ke folder `public/` yang salah struktur (atau tidak ada artinya sama sekali untuk project tersebut).
**Penyebab (Root Cause):** `ProjectManager.detect_framework()` (`core/services/project.py`) hanya memeriksa **nama file secara heuristik**, bukan isi project yang sebenarnya:
```python
if "artisan" in files and "composer.json" in files: return "laravel"
if "spark" in files and "public" in files: return "codeigniter"
```
`"artisan"` hanyalah NAMA file/folder — bukan properti eksklusif Laravel. Project custom (termasuk yang berbasis Zend yang dimodifikasi) bisa saja punya skrip CLI custom yang kebetulan dinamai `artisan`, dan hampir semua project PHP modern (termasuk yang bukan Laravel) punya `composer.json` untuk manajemen dependency. Begitu juga `"public"` adalah nama folder yang sangat umum dipakai banyak framework (Laravel, CodeIgniter, Symfony, Zend Expressive, Slim, dan banyak struktur custom) — bukan sinyal unik CodeIgniter. Heuristik nama-file ini tidak pernah memverifikasi apakah project BENAR-BENAR bergantung pada package `laravel/framework`/`codeigniter4/framework`.
**Solusi (Fixed):**
- Ditambahkan helper `_composer_requires(directory, package)` yang membaca `composer.json` project (lewat `read_json()` yang sudah aman terhadap file hilang/rusak) dan memeriksa apakah `package` (mis. `"laravel/framework"`, `"codeigniter4/framework"`) benar-benar terdaftar di section `require`/`require-dev` — ini adalah identitas yang stabil dan tidak ambigu di ekosistem Composer, berbeda dari sekadar menebak dari nama file.
- `detect_framework()` sekarang mensyaratkan KEDUA kondisi: nama-file heuristik LAMA (untuk kecepatan — hindari baca file kalau jelas bukan kandidat) DAN verifikasi dependency Composer yang sebenarnya, sebelum menyimpulkan `"laravel"` atau `"codeigniter"`. Project yang tidak benar-benar bergantung pada package tersebut sekarang jatuh ke `"raw"` seperti seharusnya.
- Ditambahkan test regresi baru (`test_detect_framework_custom_zend_project_with_artisan_script_is_not_laravel`, `test_detect_framework_raw_project_with_coincidental_artisan_file_is_not_laravel`) yang merepresentasikan persis skenario yang dilaporkan user, **divalidasi dengan sengaja mengembalikan kode ke versi heuristik lama** — kedua test terbukti gagal (`'laravel' == 'raw'`) di versi buggy, lalu lulus lagi setelah fix dikembalikan, sesuai `AGENTS.md` Golden Rule #21. Test `test_detect_framework_laravel`/`_codeigniter` yang sudah ada juga diperbarui untuk ikut mem-mock isi `composer.json` yang valid, supaya tetap merepresentasikan kasus true-positive.
**Pelajaran untuk ke depannya:** Mendeteksi "jenis" sebuah project (framework, tipe konfigurasi, dsb) HANYA dari nama file/folder yang ada adalah heuristik rapuh begitu nama itu bukan sesuatu yang eksklusif dimiliki satu teknologi — terutama nama generik (`public`) atau nama yang bisa ditiru/dipakai ulang oleh project custom (`artisan`). Kalau ekosistem project tersebut (di sini: Composer/PHP) punya sumber kebenaran yang lebih otoritatif (`composer.json` → `require`), verifikasi ke situ dulu sebelum menyimpulkan, alih-alih berhenti di nama file yang kebetulan cocok.

## 40. ✅ Analisa Usability: Menu "Runtimes" Salah Kategori di Sidebar, Grup "Tools" Mencampur Dua Sifat Berbeda — SUDAH DIRESTRUKTURISASI

## 41. ✅ 4 Temuan Follow-up Audit Konsistensi UI (Dropdown Terpotong Modal, Warna Tombol "Installed", Mismatch Ukuran Form) — SUDAH DIPERBAIKI
**Deskripsi:** Setelah audit konsistensi UI Fase 1-3 (lihat `docs/ui_consistency_guide.md`), user melaporkan 4 temuan dari pemakaian nyata: (1) panel dropdown `<Select>` terpotong saat dibuka di dalam modal dan isinya panjang; (2) dropdown pemilihan versi PHP saat instalasi PHP baru tidak punya kotak pencarian; (3) warna tombol status "Installed" berbeda antara modul Tunnels, Runtimes, dan Git; (4) tinggi & ukuran font label/input di modal pengaturan Database berbeda antara field dropdown dan field lainnya.

1. `components/Select.tsx`'s panel dropdown dirender `position: absolute` sebagai anak langsung dari trigger-nya. `components/Modal.tsx` membungkus `children` dalam `<div className="... max-h-[70vh] overflow-y-auto">` DAN kotak modal terluar punya `overflow-hidden` — keduanya ancestor clipping yang independen, masing-masing cukup untuk memotong panel yang posisinya absolute di dalam DOM tree tersebut.
2. `menu/php/NewInstance.tsx` secara eksplisit memasang `searchable={false}` pada `<Select>` pemilih versi PHP saat instalasi — properti ini seharusnya memang untuk kasus opsi sedikit, bukan untuk daftar versi online yang bisa panjang.
3. `InstallHeaderButton` di Tunnels (`tools/tunnels/Main.tsx`) secara eksplisit punya cabang warna `bg-emerald-500` saat `installed`. `RuntimesHeaderActions` di `runtimes/Main.tsx` TIDAK punya cabang serupa — ia cuma mengandalkan pseudo-class native `disabled:bg-slate-400` (lagipula sambil memakai hover hardcoded `hover:bg-blue-600`, bug kelas yang sama dengan yang sudah diperbaiki di tempat lain saat Fase 1), sehingga tombol "Installed" di Runtimes jatuh abu-abu, bukan emerald. Git tidak punya tombol status "Installed" sama sekali (tombol "Install Git" disembunyikan total begitu `gitData.installed` true). Sebagai bonus temuan: badge status "Installed" milik `ZrokEngineCard` di Tunnels SENDIRI ternyata ikut salah tema (abu-abu, bukan emerald) karena `Card.tsx`'s `getStatusTheme()` tidak pernah mengenali kata kunci "install" di daftar pencocokan tema sukses/hijau.
4. `menu/database/Settings.tsx`'s 13 input native memakai padding `p-2` (tinggi efektif ~38px) sedangkan trigger `<Select>` punya tinggi tetap `h-[42px]` — berbeda ~4px. Label-labelnya juga eksplisit `size="xs"` (`FieldLabel`) sedangkan label internal `<Select label="character_set_server">` memakai default `size="sm"` — beda ukuran font label yang terlihat jelas berdampingan.
**Solusi (Fixed):**
1. `Select.tsx` direfaktor memakai `createPortal` (React) untuk merender panel ke `document.body`, posisi dihitung manual dari `triggerRef.current.getBoundingClientRect()` (disimpan di state, dihitung ulang di `useLayoutEffect` saat `isOpen` berubah agar tidak ada flicker). Resize window memicu reposisi; scroll pada ancestor manapun (capture-phase listener di `window`) menutup panel alih-alih mencoba reposisi berkelanjutan — proyek ini tidak punya dependency positioning library (Popper/Floating UI), jadi close-on-scroll dipilih sebagai pendekatan pragmatis yang konsisten dengan skala proyek. Deteksi klik-di-luar (`handleClickOutside`) diperbarui untuk mengecualikan baik `containerRef` maupun `panelRef` (sebelumnya cukup satu ref karena panel adalah anak DOM dari container; dengan portal keduanya jadi subtree terpisah). Event keyboard tetap berfungsi karena portal React tetap mem-bubble event lewat REACT tree (bukan DOM tree) — `handleKeyDown` dipasang baik di container maupun wrapper panel yang di-portal-kan, karena keduanya kini sibling di React tree, bukan parent-child.
2. `searchable={false}` dihapus dari `<Select>` pemilih versi PHP di `php/NewInstance.tsx` (default `true` berlaku).
3. `RuntimesHeaderActions` diberi cabang warna sama persis dengan `InstallHeaderButton` Tunnels (`bg-emerald-500 hover:bg-emerald-600 disabled:opacity-100 disabled:cursor-default border-transparent` saat installed, `bg-primary hover:bg-primary/90 border border-transparent` saat belum) — sekaligus menghilangkan hardcoded `hover:bg-blue-600`. `Card.tsx`'s `getStatusTheme()` ditambah kata kunci `'install'` ke cabang tema sukses/hijau, sehingga badge "Installed" di `ZrokEngineCard` (dan badge serupa di modul manapun di masa depan) otomatis konsisten emerald. Git TIDAK diubah — modul ini memang tidak pernah menampilkan tombol status "Installed" yang persisten (bukan bug warna, melainkan pola UX berbeda: tombol install hilang total begitu terpasang); kalau user menginginkan Git juga menampilkan indikator serupa, itu perubahan perilaku terpisah di luar lingkup "samakan warna" yang diminta.
4. Di `database/Settings.tsx` SAJA (sesuai permintaan eksplisit, tidak menyentuh `<Select>`-nya): seluruh 13 `<input>` native diubah dari `p-2` ke `p-2.5` (≈42px, menyamai tinggi trigger `Select`), dan seluruh `<FieldLabel size="xs">` diubah ke `size="sm"` (menyamai default label internal `Select`). **Catatan:** `php/Settings.tsx` punya pola identik (`p-2` + label `size="xs"`) dan belum ikut diubah karena permintaan user eksplisit berlingkup modul Database saja — dicatat di sini sebagai kandidat follow-up kalau konsistensi ingin diperluas.
- Ditambahkan test regresi: 3 test baru untuk perilaku portal `Select` (render ke `document.body` bukan di ancestor yang clipping, tutup saat scroll, klik di dalam panel tidak dianggap "klik di luar") — **divalidasi dengan sengaja mengembalikan render ke versi non-portal**, test target terbukti gagal, lalu lulus lagi setelah fix dikembalikan; 1 test baru untuk kotak pencarian versi PHP; 1 baris baru di test parametrized `Card.test.tsx` untuk status "Installed" → `bg-emerald-100`.

**⚠️ Koreksi (ditemukan dari smoke test manual setelah fix di atas dipasang):** Listener `scroll` capture-phase di `window` (poin 1 solusi) ternyata TERLALU AGRESIF — `addEventListener(..., true)` di capture phase menjangkau event `scroll` dari DESCENDANT manapun, termasuk listbox opsi `role="listbox"` **di dalam panel itu sendiri** (`max-h-[180px] overflow-y-auto`), meski event `scroll` tidak bubble. Akibatnya: menggulir daftar opsi yang panjang di dalam dropdown (bukan menggulir ancestor di luar panel) ikut menutup panelnya sendiri — persis kebalikan dari yang diinginkan. Diperbaiki dengan mengecualikan scroll yang `event.target`-nya berada di dalam `panelRef` (`panelRef.current?.contains(event.target)`), dengan guard tambahan `event.target instanceof Node` karena `event.target` bisa berupa `window`/`document` (bukan `Node`) saat yang di-scroll adalah halaman penuh, dan `Node.prototype.contains()` throw `TypeError` kalau argumennya bukan `Node`. Test regresi baru `'does NOT close the panel when scrolling the options listbox itself'` ditambahkan, **divalidasi dengan sengaja mengembalikan `handleScroll` ke versi tanpa pengecualian panel** — test terbukti gagal (listbox hilang padahal seharusnya tetap ada) persis seperti laporan user, lalu lulus lagi setelah fix dikembalikan.
**Pelajaran untuk ke depannya:** Dropdown/popover custom yang dirender `position: absolute` **akan selalu berisiko terpotong** begitu dipakai di dalam container manapun yang punya `overflow-hidden`/`overflow-y-auto`/`overflow-scroll` di ancestor manapun (modal, panel scrollable, dsb) — kalau komponen tsb dipakai luas lintas aplikasi (seperti `Select` di sini), portal ke `document.body` dengan posisi dihitung manual adalah pola yang lebih tahan lama daripada menambal CSS di satu tempat pakai. Saat menambahkan cabang warna kondisional baru untuk sebuah state (mis. "installed"), selalu grep literal status text yang sama (di sini "Installed") ke semua tempat yang memakai pencocokan keyword generik (`Card.tsx`'s `getStatusTheme`) — kalau tidak, komponen bersama yang seharusnya otomatis konsisten malah diam-diam tetap berbeda di satu tempat. Soal listener capture-phase di `window` untuk "tutup saat scroll di luar": **capture phase menjangkau SEMUA descendant tanpa peduli bubbling**, jadi kalau komponennya sendiri punya area scrollable internal (seperti listbox opsi di sini), WAJIB filter berdasarkan `event.target` untuk membedakan "scroll di dalam komponen sendiri" vs "scroll di ancestor luar" — smoke test manual (bukan cuma unit test) penting justru untuk menangkap kelas bug interaksi seperti ini, yang mudah lolos dari test otomatis kalau skenario spesifiknya (scroll konten internal yang panjang) tidak eksplisit ditulis sejak awal.

**Temuan lanjutan (follow-up kedua dari smoke test manual):** Highlight baris opsi yang SEDANG TERPILIH di dalam panel `Select` (`SelectOptionRow`) memakai `bg-blue-50 dark:bg-blue-900/30 ... dark:text-blue-400` — hardcoded, bukan token theme-aware, persis kelas bug `bg-blue-*`/`dark:text-blue-400` yang sudah diperbaiki di banyak tempat selama Fase 1. Diperbaiki ke `bg-primary/10 dark:bg-primary/20 text-primary` (tanpa `dark:` terpisah untuk warna teks karena `text-primary` sendiri SUDAH theme-aware penuh — `--theme-primary` di-switch lewat atribut `[data-theme]`, bukan lewat strategi dark-mode Tailwind), menyamai konvensi "item aktif" yang sudah dipakai di tab sidebar `SettingsModals.tsx` (`bg-primary/10 text-primary dark:bg-primary/20`). Test regresi baru ditambahkan, **divalidasi dengan sengaja mengembalikan ke kelas hardcoded lama** — test terbukti gagal, lalu lulus lagi setelah fix dikembalikan.
**⚠️ Catatan skala:** Grep lanjutan menemukan pola `bg-blue-*`/`text-blue-*` hardcoded serupa tersebar di **puluhan lokasi lain** di luar `Select.tsx` (badge info di `Card.tsx`'s tema biru, kotak peringatan `database/ChangePassword.tsx`/`php/NewInstance.tsx`, badge versi di `dashboard/Main.tsx`, dsb) — beberapa di antaranya memang theme-aware di teks (`text-primary`) tapi background/border-nya tetap biru statis. Ini DILUAR lingkup laporan user (spesifik dropdown) sehingga TIDAK ikut diubah di sini — dicatat sebagai kandidat audit lanjutan kalau konsistensi tema ingin diperluas ke seluruh aplikasi secara menyeluruh, bukan cuma komponen `Select`.

## 45. ✅ Fitur Histori Toast (Bell Icon) + Notifikasi Native Windows — DITERAPKAN, 2 Bug Nyata Ditemukan Saat Implementasi
**Deskripsi:** Fitur baru: `NotificationBell.tsx` di footer Sidebar menampilkan riwayat toast (`ToastContext.tsx` diperluas dengan `history`/`unreadCount`/`clearHistory`/`markHistoryRead`, session-only, cap 100 entri), terintegrasi dengan notifikasi native Windows (`win11toast`) yang HANYA tampil saat window backgrounded (tidak fokus/minimized/hidden ke tray, lewat hook baru `useWindowPresence.ts`). Entri ini fokus ke **dua bug nyata** yang ditemukan (bukan cuma diasumsikan) lewat regresi test selama implementasi, bukan di tahap desain.

**Bug #1 — `showToast` kehilangan stabilitas referensial, memicu re-fetch tak terduga di 120+ call site:**
Implementasi awal menaruh `isBackgrounded`/`desktopNotificationsEnabled` di dependency array `useCallback` milik `showToast`, supaya closure-nya selalu baca nilai terbaru. Ini SECARA TAK SENGAJA membuat identity `showToast` berubah setiap window fokus/blur berganti — dan banyak komponen existing (mis. `apache/Settings.tsx`) menaruh `showToast` di dependency array `useEffect`-nya SENDIRI (pola "fetch sekali saat mount + toast error"), sehingga setiap kali `showToast` berganti identity, efek-efek itu **ikut re-run**, memicu refetch di tengah interaksi user. Terdeteksi lewat `tests/menu/apache/Settings.test.tsx` — 8 dari 14 test gagal ("Unable to find option Apache 2.4.58") SETELAH test lain dalam file yang sama berinteraksi dengan dropdown `<Select>`-nya (klik trigger → fokus bergeser → `isBackgrounded` sempat flip → `showToast` berganti identity → `fetchInstalledVersions()` re-run di tengah klik berikutnya → dropdown reset/tertutup). Diisolasi lewat `git stash` (hanya `ToastContext.tsx`) yang membuktikan baseline tanpa perubahan ini 100% lulus.
**Fix:** `showToast` (dan `clearHistory`/`markHistoryRead`) dibungkus `useCallback` dengan dependency array **tetap `[]`** seperti semula — state yang berubah-ubah (`isBackgrounded`, `desktopNotificationsEnabled`) dibaca lewat `useRef` yang di-sync tiap render (`isBackgroundedRef.current = isBackgrounded`), bukan ditambahkan ke dependency array. Kontrak ini sekarang didokumentasikan eksplisit di `docs/frontend_ui.md` §5.5 supaya tidak terulang saat fitur berikutnya menambah state ke `ToastProvider`.

**Bug #2 — `window.addEventListener('blur', ...)` false-positive saat elemen PERTAMA di halaman menerima fokus (bukan OS-level blur sungguhan):**
`useWindowPresence.ts`'s `handleBlur` awalnya langsung `setHasFocus(false)` setiap event `blur` di-terima di level `window`. Ternyata `userEvent.click()` (dan juga interaksi nyata di browser/Chromium/WebView2) bisa memicu event `blur` di level **window** murni karena perpindahan fokus ANTAR ELEMEN DI DALAM HALAMAN YANG SAMA — ini bagian dari prosedur *focus target adjustment* di spec UI Events (W3C), yang diterapkan browser (dan jsdom, terverifikasi lewat `node_modules/jsdom/.../focusing.js`) saat sebelumnya belum ada elemen yang betul-betul fokus (`document.activeElement` masih default). Akibatnya `isBackgrounded` sempat `true` padahal window sebenarnya tetap fokus penuh — persis skenario yang memicu Bug #1 di atas. Ditemukan lewat debugging bertahap (`console.log` di dalam `handleBlur`, termasuk `new Error().stack`) yang menunjukkan trace persis `userEvent.click()` → `HTMLElement.focus()` → `fireFocusEventWithTargetAdjustment` → `window` 'blur'.
**Fix:** `handleBlur` tidak lagi percaya mentah-mentah ke event `blur` itu sendiri — cross-check ke `document.hasFocus()` sebagai sumber kebenaran (`setHasFocus(document.hasFocus())`). Kalau window SEBENARNYA masih fokus (target-adjustment edge case), nilai ini tetap `true`; kalau benar-benar blur OS-level (alt-tab, dsb.), `document.hasFocus()` juga akan `false` di titik itu, jadi perilaku untuk blur sungguhan tidak berubah. Test regresi baru `'ignores a spurious window blur when document.hasFocus() still reports true'` di `tests/hooks/useWindowPresence.test.ts`, **divalidasi dengan sengaja mengembalikan `handleBlur` ke versi lama** — test terbukti gagal, lalu lulus lagi setelah fix dikembalikan.
**Implikasi untuk kode test:** Mock `document.hasFocus` di semua test terkait (`useWindowPresence.test.ts`, `ToastContext.test.tsx`) harus **stateful** (`vi.spyOn(document, 'hasFocus').mockImplementation(() => focused)` dengan variabel `focused` yang di-toggle helper `simulateBlur()`/`simulateFocus()`), bukan `mockReturnValue(true)` statis — kalau statis, cross-check di atas membuat `simulateBlur()` berbasis event mentah jadi tidak pernah benar-benar mengubah apa pun. Test integrasi "backgrounded" lain (showToast → native notification) sengaja memakai jalur `vylo_window_state` (`minimized`) alih-alih `blur` sama sekali, untuk menghindari nuansa jsdom ini secara total.

**Bug minor #3 — Duplikasi `get_app_settings()` fetch (ditemukan sebelum sempat jadi regresi test, langsung diperbaiki di desain):** Rancangan awal `ToastProvider` memanggil `api.get_app_settings()` sendiri untuk tahu nilai `enable_desktop_notifications` saat mount — ini fetch DUPLIKAT (App.tsx sudah memanggilnya sekali saat boot untuk theme/language) yang juga "mencuri" satu slot `mockResolvedValueOnce()` di banyak test lain yang mem-mock `get_app_settings` dengan urutan response spesifik untuk komponennya sendiri (terdeteksi lewat `App.test.tsx`'s `toHaveBeenCalledTimes(1)` gagal). **Fix:** `ToastProvider` TIDAK memanggil `get_app_settings()` sendiri — `App.tsx` mem-broadcast nilai `enable_desktop_notifications` lewat event `vylo_desktop_notifications_changed` (event yang sama dipakai `SettingsModals.tsx` untuk live-update) setelah fetch awalnya sendiri sukses. Satu event, dua emitter (initial load + live toggle), satu listener.

**Pelajaran untuk ke depannya:** (1) Referensial stability sebuah fungsi yang di-expose lewat Context dan dipakai luas (120+ call site) adalah KONTRAK IMPLISIT yang mudah dilanggar tanpa sadar begitu fungsi itu perlu membaca state baru — selalu pertimbangkan `useRef` dulu sebelum menambah dependency ke `useCallback`/`useMemo` yang hasilnya di-expose lewat Context Provider yang dipakai luas. (2) `window.addEventListener('blur'/'focus')` TIDAK bisa diasumsikan 1:1 dengan "window OS-level kehilangan/mendapat fokus" — selalu cross-check ke `document.hasFocus()` sebagai sumber kebenaran, terutama untuk fitur yang baru pertama kali membaca state fokus di codebase ini. **Bug #2 — Crash download, PRA-EKSISTING (bukan regresi dari fitur #45), sudah ada di `HEAD` sebelum sesi ini dimulai:** `core/utils/file_utils.py`'s `download_advanced()`/`extract_archive()` (dipakai SEMUA modul download) memanggil `progress_cb` dengan **3 argumen posisional** `(percent, message_key, args_dict)` di beberapa titik (`_extract_zip` saat melaporkan index/total file; `_download_multi_part`/`_download_single_stream` saat melaporkan persentase sub-step) — perubahan ini masuk di commit `5b2f7f8` ("Add Tunnels (Zrok) module, theming system, and backend hardening fixes"), commit TERAKHIR di `HEAD` sebelum sesi kerja ini dimulai. - Ditambahkan 5 test regresi baru (satu per file: `test_apache.py`, `test_database.py`, `test_php.py`, `test_git_manager.py`, `test_runtimes_manager.py`), masing-masing memanggil closure-nya langsung dengan 3 argumen posisional (meniru persis pola panggilan nyata `file_utils.py`) dan memverifikasi tidak `TypeError` DAN `args` diteruskan dengan benar ke `emit_progress`. **Divalidasi dengan sengaja mengembalikan `runtimes_manager.py`'s `download_cb` ke versi 2-parameter** — test representatif (`test_get_cbs_download_cb_forwards_three_positional_args`) terbukti gagal dengan pesan error **PERSIS SAMA** dengan laporan user (`takes 2 positional arguments but 3 were given`), lalu lulus lagi setelah fix dikembalikan. 3 test lama yang mem-assert pemanggilan `emit_progress`/`_emit_progress` dengan 2 argumen eksplisit (`test_install_git_download_progress_is_clamped_not_scaled`, `test_php_install_version_configuring_step_is_not_terminal_progress`, `test_get_cbs`) diperbarui untuk menyertakan argumen ketiga (`None` atau menggunakan unpacking `*_` yang toleran) — bukan perbaikan bug, cuma penyesuaian asersi mengikuti signature baru yang benar.
